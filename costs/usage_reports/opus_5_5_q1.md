## 3. 解读

1. **输入几乎全部来自缓存读取。** 每次 API 请求都要把整个对话上下文重新送给模型。上下文前缀已缓存时按"缓存读取"计。研究后半段上下文有 30–50 万 token，又是大量小步工具调用（第 4 段 67 个请求），所以缓存读取累计到 4,646 万，而真正新写入缓存的只有约 51 万。
2. **输出以 thinking 为主（81%）。** 最大的单笔是 09:38 的一次请求：128,000 token 全部是 thinking，撞到单次输出上限（即对话中的"Output token limit hit"）。仅这一次就占全部输出的 24%。之后改为小步推进，单次输出明显变小。
3. **第 1 段输出占 2/3**（推导理论框架、设计计算方案）。第 4 段请求最多、缓存读取最多（占 66%），但输出只占 21%，主要是跑计算、读结果、改报告。
